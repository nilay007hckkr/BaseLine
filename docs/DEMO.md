# Hindsight: Demo script (3 minutes) and judge Q&A

PS 06 (Project Brain) is the core and fills the 3 minutes. Incidents (PS 04) and Tests (PS 08) are
built on the same graph and shown as **additional features** after the core, or when judges ask
(they sit after a divider in the top bar; `SHOW_FROZEN=false` hides them).

**Setup on stage:** `make start` (`LIVE=1` if the shop's cluster is not up yet, for live
Incidents), dashboard open on Home (tour skipped; **Tour** replays it). Run the PR check once
before going on stage, so it is cached if the venue Wi-Fi or GitHub's rate limit fails. Every
question below was run on the real data; the numbers quoted are from
`eval/results/ask-20261031T230652Z.json` and `impact-20261030T185851Z.json` (re-read them from
**Proof** on the day).
**Fallback:** quoted answers work with no model and no network; the PR check falls back to its cached copy.

## Judge Q&A

- **"Isn't this just RAG over a repo?"** Three differences. (1) The graph comes first: blame → commit → PR → issue → discussion, with provenance on every edge; search only fills gaps. (2) Code decides: ranking, citations and "not found" are code; the model only phrases evidence code already selected, and claims that are not supported by their cited text are dropped. (3) It is measured against baselines, including where it loses.
- **"How do you avoid grading your own answers?"** The answerable questions are generated by code from explicit "Fixes #N" links, so we do not pick them; the trick questions are written by hand and committed before they are first scored (git shows the order); 10 answers go to a person in a CSV. Protocol: `docs/EVALUATION.md` §3.
- **"Why is naming the commit 100%?"** Because the graph links the commit to its issue: that is connected memory working. The honest test is the second variant (file and change only), where we are at 60% and show the failure analysis (busy files such as README.md where many commits share the words).
- **"Isn't co-change just noise?"** Raw co-change is noisy. We filter bots, sweeps and merges, fuse it with service calls read from the code, and replay held-out history. On Online Boutique the gain over co-change alone is within the confidence interval; on the OpenTelemetry Demo (n = 140) it is larger (R@10 0.356 vs 0.290, Hit@3 0.45 vs 0.34), with intervals that still touch. The main win is over the folder baseline, plus a reason for every item.
- **"What if the model hallucinates?"** It never decides anything. A claim must cite evidence ids that exist and share its key words with the cited text, or it is dropped; with no surviving claim the answer is quoted word for word or "not found".
- **"Does it work offline?"** Yes: Gemini → Groq → local Ollama, and with no model at all, quoted answers. The PR check and stale-doc flags never use a model.
- **"Stale docs: false positives?"** It is a signal, not a verdict: "3 or more commits by people changed what this doc describes after its last edit", with the commits listed so a person can judge in seconds.
- **"Does it scale / work on other repos?"** The workspace connects any public GitHub repository and measures the impact check on that repo's own history. The same replay ran on dotnet/eShop and the OpenTelemetry Demo with untuned weights. Neo4j and SQLite are tested to answer identically.

**On the additional features**
- **"How do you know the healer doesn't hide bugs?"** It never touches assertions, refuses when there is backend error evidence, needs a score margin over the next candidate, and every repair waits for a person. False heals are measured on injected real defects: 0.
- **"Victim vs culprit?"** The frontend logs the most errors, but its messages name the failing callee and the call graph points downstream; the culprit is ranked by code, not by error count.
- **"Is the incident → change link causal?"** No. It is a ranked candidate with its evidence (timing, whether the change touched the broken service, whether the impact check predicted it).
- **"Why are these not the main pitch?"** They reuse the same graph and evidence rules, but they are measured only on faults we inject into a local shop; PS 06 is measured on the project's real history.

- Learned impact ranker, trained by history replay
- Contradiction detection between docs and code
